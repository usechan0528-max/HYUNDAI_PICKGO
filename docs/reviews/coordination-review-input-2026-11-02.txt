# 공동 이용 조율 에이전트 심층 평가

작성: Codex · 기준일: 2026-11-02 KST · 상태: 조사 기반 자체 평가, 실사용 검증 전

## 판정

현재 기획은 사용자가 정한 공모전 자체 기준을 통과하지 못한다. 공식 4개 평가항목에 대한 보수적 자체 점수는 **차량 특화성 80 / 창의성 65 / 기술 활용성 55 / 사업성 60, 단순 평균 65점**이다. 70점 이하 과락 기준에 3개 항목이 해당한다. 이는 공식 심사 점수나 합격 확률이 아니다.

**권고: 공동 이용 조율을 주력 제품으로 확정하고 본 구현을 확대하기 전에, 반복 수요와 최소 실행 권한을 검증한다.** 현재 가설을 사용자가 폐기하거나 새 주제로 바꾸기로 결정한 것은 아니다.

앞선 추천은 범용 차량 에이전트보다 구별되는 가설이라는 판단이었다. 그때 반복 사용성·실행 권한·입력 부담을 충분히 입증하지 못했다. 이번 평가에서는 그 가설 자체를 반증 대상으로 삼았다. 제품 잠재력과 현재 증거를 구분하며, 앱이 아직 없다는 이유만으로 감점하지 않는다. 감점의 핵심은 필요한 권한이 불확실하고, 대표 시나리오의 추가 가치가 약하며, 범용 이용이라는 목표와 대상이 어긋나는 점이다.

## 범위와 사용자 결정

- 유지할 목표: 자동차 지식이 적어도 차량 기능·서비스 전반을 쉽게 이용하게 한다.
- 검증 가설: 여러 탑승자의 요청·조건·변경·취소를 관리하면 운전자가 대신 처리하는 부담을 줄일 수 있다.
- 사용자는 추천 방향의 진행을 요청한 뒤 심층 평가를 추가 요청했다. 조사·평가를 진행하며, 완성 앱의 전체 범위가 승인되었다고 확대 해석하지 않는다.
- 실차 접근: 사용자가 잠시 가능하다고 답했으나 바로 **이용할 수 없음**으로 정정했다. Gleo 실제 비교 결과는 없다.
- 시행한 것: 공식 문서·논문 초록/공개 원문 조사, 환경 점검, 평가 및 검증 설계.
- 시행하지 않은 것: 차량 제어, SDK 다운로드·빌드, 에뮬레이터, 사용자 실험, Gleo 실차 시험, 외부 문의 발송. 모의 프로토타입도 아직 만들지 않았다.

## 평가 방식

공식 평가항목은 차량 특화성, 창의성, 기술 활용성, 사업성이다. 공식 비중은 공개되지 않는다. 여기서는 사용자가 요청한 각 100점 및 단순 평균을 적용한다. 평균 90 이상·모든 항목 70 초과를 통과 조건으로 삼는다. [공식 심사 기준](https://appdevchallenge.auto-hmg.io/guide/judging-awards)

점수는 대략적인 판단 구간을 표현하기 위해 5점 단위로 사용한다. 90점대는 중대한 반대 근거가 해소되고 강한 차별성과 실행 가능성을 설명할 수 있는 상태, 75~85점은 유망하지만 검증 과제가 있는 상태, 60~70점은 주요 가설이 미입증이거나 상당한 중복이 있는 상태, 55 이하에는 핵심 실현 조건의 불확실성이 포함된다. 공모전의 공식 채점표가 아니라 이번 의사결정을 위한 기준이다.

| 항목 | 점수 | 긍정 근거 | 감점 이유 | 점수를 바꿀 증거 |
|---|---:|---|---|---|
| 차량 특화성 | 80 | 여러 좌석이 경로·음향·차량 상태를 공유하는 맥락은 차량에서 중요 | 실제 실행 연동 없이 요청 수집만 하면 휴대전화로도 가능. 단독 탑승자 가치는 약함 | 실제 차량 상태에 따라 결과가 달라지고 기존 조작보다 부담이 줄어드는 흐름 |
| 창의성 | 65 | 동시 요구의 충돌·만료·동의를 명시적으로 관리하는 구체성 | 음성 이해·좌석 구분·복합 실행은 Gleo와 중복. 운전자-동승자 협업과 LLM 협상도 선행 연구 존재 | 최신 Gleo가 처리하지 못하는 실제 사례와 그에 대한 반복 가능한 개선 |
| 기술 활용성 | 55 | 내비 연동·UX 제한·Gleo 앱 호출은 공개 문서에 기반이 있음 | 대표 음향 시나리오의 실행 권한 미확인. 오디오 포커스로 다른 앱/후석 스피커를 자유 제어할 수 없음 | 배포 가능한 권한으로 핵심 기능의 읽기→실행→결과 확인 성공 |
| 사업성 | 60 | 가족·카풀·동료 동승처럼 명확한 초기 후보군 | 빈번한 동승이 빈번한 조율 필요를 뜻하지 않음. 가입·요청·동의 비용과 무료 기본 기능 대비 지불 이유 미확인 | 무갈등 이동까지 포함한 이용 일지, 실제 재사용, 도입 의사 또는 유통 파트너 근거 |
| 단순 평균 | **65** | | **현재 기준 미달, 3개 항목 과락** | |

추가 사용자 조건에 대한 판단: 휴대전화 대비 우위는 실제 연동을 전제로 한 조건부, 기본 서비스와의 비중복은 미입증, 현대차의 앱 생태계·차량 이용 경험 확장 방향과의 관련성은 높음, 사용자 편의·안전 지향과의 정합성은 실제 상호작용 부담 감소를 확인해야 한다. 전략적 관련성이 높다는 사실은 이 앱을 현대차가 채택할 것이라는 증거가 아니다. ## 1. 원래 문제와 현재 문제의 차이

원래 문제는 **사용자가 기능·서비스를 몰라서 활용하지 못하는 지식 공백**이다. 공동 이용 조율은 **여러 사람의 요구가 충돌하거나 흩어져 있는 상황**을 해결한다. 후자는 전자를 포함할 수 있지만 같은 문제는 아니다.

‘차량의 모든 기능을 대상으로 한다’는 기능 범위가 ‘많은 운전자에게 자주 필요하다’는 이용 범위를 보장하지 않는다. 혼자 타는 날에도 쓰도록 일반 추천·음성 제어를 붙이면 다시 Gleo와의 중복이 커진다. 가족이 자주 동승하더라도 평소 설정이나 짧은 대화로 해결하면 전용 조율 앱의 효용은 작다.

## 2. 반복 사용성의 실제 조건

주간 유효 이용 기회는 다음 조건의 결합으로 생각할 수 있다. 독립이라고 가정하지 않으며 수치를 임의로 채우지 않는다.

`전체 이동 수 × P(동승) × P(조율 필요 | 동승) × P(기존 수단보다 앱이 유리 | 조율 필요) × P(지원 기능·권한 확보 | 해당 상황)`

현재 어느 조건에도 대상 사용자 집단의 실측값이 없다. 단순 동승률, 차량 판매량, 설치 가능 대수만으로 MAU나 리텐션을 예측하면 안 된다. ‘뒤에서 쉬고 앞에서 음악 듣기’도 처음 설정한 후 계속 쓰는 기본 모드라면 전용 앱의 반복 개입이 필요하지 않을 수 있다.

| 사용자군 | 가능성 | 핵심 반대 가설 |
|---|---|---|
| 가족이 자주 함께 이동 | 아이·보호자·운전자 요구가 달라질 수 있음 | 보호자의 한마디나 기본 설정으로 해결 가능 |
| 출퇴근 카풀 | 참여자·하차 위치·시간 조건이 반복 | 일정한 경로에서는 매번 조율할 필요가 적음 |
| 친구와 여행 | 여러 서비스 요구가 발생할 수 있음 | 사용 빈도가 낮고 앱 참여 절차가 번거로울 수 있음 |
| 혼자 운전 | 일반 기능 안내를 제공할 수 있음 | 공동 조율이라는 핵심 가치가 발생하지 않음 |

앱을 다시 열겠다는 설문 의향과 실제 재사용은 구분한다. 알림을 많이 보내 이용 횟수를 늘리는 것은 성공으로 계산하지 않는다.

## 3. Gleo 및 기본 기능과의 차이

Gleo는 자연어/간접 표현, 복합 요청, 좌석 위치 구분, 차량 상태를 고려한 제어를 공식적으로 설명한다. 장기 기억·선제 제안은 공개 발전 방향이다. 다중 사용자 요구의 유효기간·동의·충돌 해결을 우리 방식으로 지속 관리하는 전체 제품 흐름은 검토 자료에서 확인하지 못했지만, 이것을 현재 Gleo의 미지원으로 단정할 수 없다. [개발자 설명](https://www.hyundaimotorgroup.com/ko/story/42dot-gleo-ai-developer-present-and-future)

2026-10-30 OTA에는 경로 맥락을 고려한 장소 검색, 여러 경유지 정보, 연결 상태에 따른 음악 재생 개선이 포함됐다. 이전 자료의 한계를 그대로 최신 버전에 적용하면 안 된다. [공식 OTA](https://www.hyundaimotorgroup.com/ko/news/42dot-gleo-ai-first-ota-in-car-ai-experience-upgrade)

| 시나리오 | 이미 있는 대안 | 추가 가치 후보 | 현재 판단 |
|---|---|---|---|
| 뒷좌석 휴식·앞좌석 음악 | 후석 취침 등 차량 기본 기능, 음성 제어 | 반복 요청 간 충돌·만료 관리 | 단일 명령으로 해결되면 독립 앱 가치 약함 |
| 두 명의 경유 요청 | Gleo·내비 경유지 기능, 동승자 구두 조율 | 각 요청자의 조건과 변경 이력 관리 | 검색·경유지 기능 자체는 차별점 아님 |
| 온도 선호 차이 | 좌석별 설정·Gleo | 공유 자원에 대한 합의 관리 | 단순 좌석별 제어를 조율로 재포장하면 중복 |
| 이동 종료 후 이전 요청 제거 | 앱 내부 세션 관리 | 오래된 요청의 재실행 방지 | 필요한 품질 기능이나 설치를 유도하는 주력 효용인지는 미확인 |

기본 기능 존재의 근거로 사용한 [ccNC 설명서](https://ownersmanual.hyundai.com/ivi/ccNC/AVNT/KOR/Korean/)는 후석 취침 등을 열거한다. 이는 특정 Pleos 차종의 적용 사양이나 서드파티 접근 가능성을 입증하지 않는다.

정확한 출처·심볼·권한·검증 상태는 [API_EVIDENCE.md](API_EVIDENCE.md)에 분리했다.

| 좌석별 음향·후석 취침 제어 | 검토한 Pleos 공개 자료에서 앱용 계약 미확인 | 대표 시나리오의 가장 큰 기술 위험 |
| 앱 전체의 재생·볼륨 통제 | 오디오 포커스 정책은 존재. 범용 제어 권한의 근거가 아님 | 가짜 성공 처리나 포커스 선점으로 대체하면 안 됨 |
| Gleo를 통한 우리 앱 호출 | App Schema/Action/Callback 구조와 검토 승인 절차 확인 | 음성 진입점 후보. Gleo 대화 전체나 모든 제어를 가져오는 API가 아님 |
| 탑승자 신원·좌석·성인/보호자 권한 | 해당 앱에 제공되는 식별·인증 계약 미확인 | 초기에는 명시적 역할 입력이 필요. 입력 부담 발생 |
| 주행 UX·백그라운드 | CarUxRestrictions와 수명주기 정책 확인 | 무제한 상주·상시 청취·팝업을 전제할 수 없음 |

AAOS의 앞뒤 음향 균형 조절은 `CarAudioManager.setFadeTowardFront(float)`라는 **시스템 API**로 설명되며 `CAR_CONTROL_AUDIO_VOLUME` 권한이 필요하다. AAOS 기반이라는 이유로 일반 Pleos 앱에서 쓸 수 있다고 볼 수 없다. 또한 음향 구역과 실제 소리 분리는 하드웨어·OEM 구성에 의존한다. ‘앞좌석 음악, 뒷좌석 완전 무음’을 소프트웨어만으로 보장해서는 안 된다. [AOSP Audio control HAL](https://source.android.com/docs/automotive/audio/audio-control-hal), [Volume management](https://source.android.com/docs/automotive/audio/volume-management)

기존 프로젝트 기준은 초기 물리적 차량 제어를 제외한다. 향후 직접 제어를 제품 범위에 포함하려면 별도 범위 결정과 실제 권한·동작 검증이 필요하다. 현재의 미확인은 영구적 구현 불가능 판정이 아니다.

## 5. 편의성과 주의 분산

이 앱의 효용은 ‘운전자 대신 처리한 요청 수’가 아니라 **기존 방법 대비 전체 부담의 순감소**로 판단해야 한다.

`순효용 = 기존 검색·설명·조작 부담 − 참여·역할 지정·요청 입력·합의·승인·오류 복구 부담`

가족끼리 한마디로 끝나는 일을 앱 입력, 요청자 동의, 운전자 승인, 완료 알림으로 바꾸면 더 번거로울 수 있다. 매번 승인을 요구하면 부담 감소가 약해지고, 승인을 생략하면 동의하지 않은 설정 변경 가능성이 커진다. 이것은 문구 변경보다 제품 정책과 인터랙션 설계로 해결해야 할 문제다.

연구는 가능성과 반대 근거를 함께 보여준다.

- 2023년 연구는 16쌍의 시뮬레이터 실험에서 협업 방식에 따른 연결감·팀 성과·공정성 차이를 보고하고, 동승자 전용 화면의 이점을 설명한다. 그러나 우리 앱, Gleo 대비 성능, 일반 운전자 시장 수요를 검증한 연구는 아니다. [대학 연구 기록](https://research.tue.nl/en/publications/empowering-driver-passenger-collaboration-designing-in-car-system/)
- 2022년 연구는 비교한 협업 UI에서 팝업과 동승자 화면 조작이 주의를 분산시키고, 일부 이중 화면 구성이 부담을 높일 수 있음을 보고한다. 조건이 다른 연구 결과를 묶어 협업 UI가 항상 안전하거나 항상 위험하다고 결론 내릴 수 없다. [대학 연구 기록](https://research.tue.nl/en/publications/together-distracted-the-effect-of-driver-passenger-collaboration-/)
- 2024년 연구에는 운전자-동승자 갈등 설문과 LLM을 이용한 승객-자율주행차 협상이 이미 등장한다. 이는 관련 발상이 완전히 새롭다는 주장에 반대 근거지만, 현재 수동 운전 차량의 다중 탑승자 앱과 같은 제품은 아니다. [공개 연구 원문](https://www.uni-ulm.de/fileadmin/website_uni_ulm/iui.inst.100/1-hci/hci-paper/2024/AutoUI24_ConflictResolutionStrategies_preprint.pdf)

AI는 누가 양보해야 하는지 임의로 결정하지 않는다. 명시된 조건을 동시에 만족할 수 없으면 영향을 받는 사람에게 선택을 돌려줘야 한다. 경고음·운전 안전 정책은 사람 간 선호 조율의 대상이 아니다. 앱 안의 역할 정책이 차량 전체·Gleo·다른 앱의 권한을 통제한다고 표현하지 않는다.

## 6. 사업성·현대차 적합성

현대차의 개방형 앱 생태계와 차량 내 이용 경험 확대에는 부합한다. 그러나 기본 에이전트와 겹치는 기능일수록 소비자는 별도 앱 설치·구독 이유를 느끼기 어려울 수 있다. 소비자 지불 의향, OEM 도입 의향, 사용자 확보 비용, MAU와 리텐션은 모두 미측정이다.

OEM 통합 기능으로는 좌석·계정·오디오 정책에 접근할 여지가 크지만, 공모전 서드파티 앱과는 다른 사업·권한 조건이다. ‘현대차가 관심을 가질 수 있다’와 ‘현재 앱으로 납품할 수 있다’를 분리한다. 유료 서비스 추천으로 수익을 만들 경우 추천 품질·이해관계 문제도 제품 설계에 반영해야 하며, 현 단계 수익모델로 확정하지 않는다.

전체 기능·서비스로 확대할수록 어댑터, 차종별 조건, 서비스 가입·결제, 결과 확인 계약, 개인정보 처리 비용이 증가한다. 내비 한 흐름이 동작해도 나머지 서비스를 쉽게 붙일 수 있다는 증거가 되지 않는다.

## 7. 검증 계획과 중단 조건

아래 수치는 **검증 전에 제안하는 내부 의사결정 기준**이다. 실제 성과·시장 추정·통계적 유의성 기준이 아니며, 사용자가 최종 실험 범위를 선택하기 전에 변경될 수 있다.

### V1. 실제 반복 수요

- 가족·카풀 이용자 10개 단위를 후보로, 7일간 모든 차량 이동을 간단히 기록한다. 문제가 없던 이동과 혼자 이동한 날도 포함한다.
- 최근 실제 사건, 탑승 형태, 조율 필요, 기존 해결법, 해결 부담, 기존 기능으로 해결됐는지, 앱 없이도 해결했는지를 적는다. 수면·건강·정확한 경로·실명은 수집하지 않는다.
- 탐색용 진행 기준 제안: 10개 단위 중 6개 이상에서, 별도 조율 도구가 도움이 될 수 있는 실제 문제가 일주일에 두 번 이상 확인된다. 의향 응답만으로 통과시키지 않는다.
- 달성하지 못하면 ‘보편적인 반복 사용’ 주장을 철회하고, 특정 대상용 부가기능으로 평가한다. 모집·발송은 이번 작업에서 하지 않았다.

### V2. 상호작용 부담

- 우선 6쌍의 성인으로 정지된 환경의 역할극/화면 모형을 비교한다. 음악·휴식, 경유 요청 변경, 요청 취소 3개 과제와 충돌 없는 대조 과제를 포함한다.
- 비교군: 평소 구두 조율 및 기본 기능 이용 방식, 제안 앱. 실제 차량이 없으므로 이를 Gleo 비교나 주행 안전 검증으로 부르지 않는다.
- 순서를 교차 배치하고 초기 참여 절차와 오류 복구까지 측정한다. 말/화면 조작 횟수, 운전자 개입 시간, 요청 만족, 오작동·불필요한 알림을 각각 기록한다.
- 탐색용 진행 기준 제안: 문제 과제의 운전자 개입 시간 중앙값이 30% 이상 줄고, 전체 참여 시간 중앙값이 늘지 않으며, 충돌 없는 과제에서는 조작을 추가하지 않는다. 6쌍은 탐색용으로 통계적 일반화를 하지 않는다.
- 0초 기준값은 감소율을 계산하지 않고 절대 변화와 추가 부담으로 평가한다. 동의 없는 실행·권한 오인·성공 오표시는 한 건도 허용하지 않는다.

### V3. 배포 가능한 핵심 API

- 후석 음향 또는 선택한 다른 핵심 기능의 조회·실행·결과 확인 계약과 공모전 앱의 권한 취득 경로를 확인한다.
- 소스/SDK 선언과 최소 실행 시험을 확보하기 전까지 ‘연동 가능’ 점수를 올리지 않는다. 에뮬레이터 확인과 실차 확인을 구분한다.
- 확인 질문 초안: (1) 일반 공모전 앱에서 후석 취침/페이더와 현재 상태를 제어·조회할 공식 API가 있는가? (2) 필요한 권한과 승인 절차, 에뮬레이터 지원은 무엇인가? (3) 다른 미디어 앱과 Gleo의 동작 이후 최종 상태를 확인할 수 있는가?
- 현재는 문의 초안만 작성했으며 전송하지 않았다. 지원이 없다면 다른 기능을 찾아 무한 확장하지 말고, 제안 핵심의 실행 가치가 유지되는지 다시 판단한다.

### V4. 실제 Gleo 비교

- 차량 접근을 확보한 뒤 차종·연식·사양·소프트웨어 버전과 네트워크 상태를 고정한다.
- ‘앞에서 음악, 뒤에서 휴식’, 요청 변경, 다른 탑승자의 상충 요청, 이동 종료 후 재개, 경유 요청 취소를 같은 출발 상태에서 시험한다. 공정하게 Gleo가 자연어로 받을 수 있는 전체 요구를 전달한다.
- 성공/실패·재질문·수동 개입·주관적 선호를 따로 기록한다. 반복 시험은 해당 버전·조건의 관찰이며 전체 차종으로 일반화하지 않는다.
- Gleo가 같은 부담 또는 더 적은 부담으로 해결하면 해당 시나리오를 차별화 근거에서 제외한다. 접근 불가 동안 이 게이트는 미실행이다.

## 다음 결정

공동 이용 조율은 **주력 후보 검증 단계**로 유지하되, 현 자료로 본 개발을 확대하거나 90점 이상으로 상향할 근거는 없다. 먼저 V1과 V3의 적은 비용 확인이 필요하다. 실패하면 원래 목표인 ‘차량 지식 공백 해소’는 유지하면서 공동 이용 조율을 핵심에서 내리는 것을 권고한다. 새 주제 확정이나 폐기는 사용자 결정이다.
