## Verdict

No P0 or P1 found by reading. The server state machine holds its stated invariants. The findings are three P2s (two concrete UI defects and one unresolved ownership question) plus P3 test and copy issues. Nothing was executed, so the UI points below are from reading `app.mjs`, `style.css`, and the tests, not from rendering.

## Invariants checked (hold by reading)

- `boarded` implies no proposal. `ready`, `propose`, and `accept` are blocked once boarded, and `board` requires `!r.proposal`.
- `arrived` and `boarded` imply `joined`. `completed` is reachable only from `boarded`.
- Every `act` check runs in one synchronous call: status, then version, then view lease, then the requestId dedup. Node's single thread means no interleaving.
- `undoArrival` is driver-only and `undoBoarding` is rider-only. Both are blocked once boarded, so the driver's arrival survives a rider's undo.
- `reject` and `withdraw` keep the arrival. Only `accept` of a changed place resets it.
- Ended rooms reject every mutation, and the status check runs before the version check.
- Client freshness is consistent with the server lease. The client's 6s window is measured from request start, and any view it holds was issued after that start. The server TTL is 8s, so an in-window view is always still valid.

## P2

**P2-1: action errors are erased on the common path.** `app.mjs`, `act`
- Evidence: the `catch` sets `$('error')` to the conflict message. The `finally` then runs `await refresh()`, and a successful `refresh` executes `$('error').textContent = ''`.
- Impact: after a rejected tap (409 "다른 변경이 있습니다…"), the message is usually cleared before the user sees it, so the tap looks like a silent no-op. It survives only when a poll is in flight, because `refresh` returns early on `polling`. That makes it intermittent.
- Minimal fix: capture the failure in a local, then set it after the refresh.
  ```js
  let failure = '';
  // in catch: failure = `${e.message} 다시 확인 후 선택해 주세요.`;
  // in finally: busy = false; render(); await refresh(); if (failure) $('error').textContent = failure;
  ```
- Confidence: high from reading. Not executed. No test covers this.

**P2-2: the stale disclosures are hidden in exactly the failure case.** `style.css`, the rule `.cockpit:has(#error:not(:empty)) .proposal p, …  .event{display:none}`
- Evidence: `#proposalText` is a `<p>` inside `.proposal`. `#lastEvent` is `.event`. Any refresh failure sets `#error`, which hides both. The comment "Preserve the three stale labels" is therefore false for those two. The client test checks `textContent`, not visibility.
- Impact: during a disconnect, the "마지막 확인 기록 · 현재 미확인" and "현재 미확인" proposal text disappear. The remaining markers (`placeLabel`, `pickupText`, `readyText`, `#connection`) still say 미확인, so this is mitigated, but it contradicts the approved freshness semantics. Separately, `@media(max-width:899px) and (max-height:780px)` already sets `.event{display:none}`. Confirm whether that is intentional.
- Minimal fix: hide only when the connection is fresh.
  ```css
  .cockpit:has(#error:not(:empty)):has(#connection:not(.stale)) .proposal p,
  .cockpit:has(#error:not(:empty)):has(#connection:not(.stale)) .event{display:none}
  ```
- Inference: whether the error row still fits at 1280×720 once these rows return is not verified. Visual QA must confirm it.

**P2-3: ownership is not attributable for some events (decision needed).** `act`, the `end` branch and the propose/accept/reject/withdraw branches.
- Evidence: the `end` branch has no `role` check, so either party can end. The `lastEvent` strings for `end`, `propose`, `accept`, `reject`, and `withdraw` name no actor.
- Impact: the rationale "lastEvent gives explicit owner" holds only for `arrive`, `board`, the undos, and `ready`. A rider ending the session shows "이번 약속을 취소했습니다" with no actor. No completion is inferred: `completed` still requires `boarded`, so the outcome is not falsified.
- Decision: confirm whether both roles may end. If yes, prefix the actor, e.g. `const who = role === 'driver' ? '운전자' : '탑승자';`, and use it in those strings. If no, add `if (role !== 'driver') throw …` to the `end` branch.

## P3

- **Weak test for "preserve ready".** The "manual arrival" test sets `ready` to false before boarding, then asserts `ready === false` afterward. That passes even if `board` clears `ready`. Set `ready: true` before boarding and assert it survives.
- **Stray token in a test regex.** `board.test.mjs`, the "proposal resolution" test, `/場所|합의/`. Use `/합의/`.
- **Misleading error code.** The `ready` branch returns 403 "탑승자만…" for a rider sending a non-boolean `ready`. Split that into a 400.
- **Copy.** The `headline` is `sr-only` and stage-agnostic, so a boarded rider hears "준비됐어요. 약속을 확인해요." No visible impact.
- **Fail-closed lag.** After an `act` error, `online` stays false until the next poll if `refresh` returns early on `polling`. This is safe but adds up to 2s of disabled controls.
- **UI and server mismatch.** The server allows `undoArrival` while a proposal is pending, but the UI disables it. `normalActions` is hidden during a proposal anyway, so this is moot.
- **End-confirmation churn.** A rider's `ready` toggle closes an open end confirmation. The version-bound design makes this safe, and the UX cost is acceptable.
