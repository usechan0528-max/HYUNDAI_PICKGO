# PICKGO 세부 설계 검수 (Claude, claude-opus-5-5, 소스 수정 없음)

검토 범위는 PICKGO_USER_FLOW 문서 전체, gleo/README.md, domain.mjs:1-105입니다. 공식 API는 직접 확인하지 않았고 Codex가 전달한 사실만 전제로 삼았습니다. 문서에서 확인한 사실과 제가 추가한 제안은 [사실] / [제안]으로 나눠 표시했습니다. 개발 모드라서 plan 파일 작성과 종료 도구는 쓸 수 없었고, 결과는 이 응답으로만 드립니다.

## 1. 주요 결함 · 반론

1. **상위 / domain.mjs:15-23 · `create`**
   - [사실] 회차는 운전자만 만들고, 장소는 고정된 `PLACES` 문자열입니다.
   - 영향: 탑승자가 요청하는 흐름, 좌표, 검색 기준 장소를 담을 자리가 없습니다. "운전자가 수락하기 전" 상태도 없습니다.
   - [제안] `request` 단계를 회차 바깥에 따로 둡니다. 운전자가 수락할 때만 회차를 만듭니다.

2. **상위 / domain.mjs:61-63 · `arrive`**
   - [사실] 도착 처리는 `joined`가 있어야 합니다.
   - 영향: 초대받은 사람이 참여하지 않은 상태에서 운전자가 출발하는 것을 허용하면, 그 회차는 도착 표시를 할 수 없고 취소로만 끝납니다.
   - [제안] 이를 의도한 정책으로 명시합니다. 미참여 상태로 회차를 닫을 때의 문구와 결과(`cancelled`)를 정합니다.

3. **중위 / domain.mjs:81-92 · `propose`/`accept`**
   - [사실] 제안 칸은 하나뿐이라 경쟁은 막힙니다. 하지만 제안에 기준 `placeRevision`이 없고, 다시 검증한 결과도 저장하지 않습니다.
   - [제안] 제안에 `baseRevision`과 `validation{ruleset, checkedAt, result}`를 넣습니다. 수락할 때 기준 revision이 그대로인지, 검증이 아직 유효한지 다시 확인합니다.

4. **상위 / Gleo 3번째 action**
   - [반론] 검색에 3번째 칸을 쓰면 남는 칸이 없습니다. 그러면 주행 중 가장 필요한 "탑승자 요청을 음성으로 수락하기"를 넣을 수 없습니다.
   - 내비 자체 음성 검색으로 검색 기준을 얻을 수 있다면(아래 G1-b), Gleo로 하는 검색은 중복일 수 있습니다.

5. **중위 / 문서 §5 · 지도 세부 조정과 초대 전송**
   - 둘 다 주행 중 제한 대상일 가능성이 큽니다. 정차 중에만 허용할지, 탑승자 휴대폰으로 넘길지를 정하지 않으면 사용 흐름 자체가 막힙니다.

## 2. 보완된 설계 [제안]

### 데이터 축 분리

- **검색 기준 장소:** 기준점일 뿐입니다.
- **후보:** `ruleset` 버전과 데이터 기준 시각을 함께 둡니다.
- **합의 승차 좌표:** `placeRevision`으로 관리합니다.
- **내비 목적지 상태:** `routeTarget.revision`과 `requested` / `confirmed` / `failed`를 둡니다.
- **위치 공유 세션:** 회차마다 동의, 만료, stale 표시를 둡니다.
- GPS나 내비 재탐색 결과가 합의 좌표를 자동으로 바꾸는 일은 없게 합니다.

### 운전자 시작 흐름

`검색 → 후보(0~3개) → 조정 → 재검증 → 확정(rev1) → 초대(sendFailed / delivered? / joined) → 경로요청 → 안내 → 도착 → 탑승 → 종료`

- **전달 여부:** 외부 전송 수단이 전달 사실을 보증하지 못하면 "전달" 상태를 표시하지 않습니다. "보냄"과 "참여"만 구분합니다.
- **미참여 상태로 출발:** 운전자가 명시적으로 눌렀을 때만 가능하게 합니다.
- **장소 변경 수락 후:** `routeTarget`만 다시 요청합니다. 실패하면 "합의 장소는 X, 내비는 이전 목적지"를 계속 보여주고 수동 재시도를 둡니다. 합의 내용은 되돌리지 않습니다.

### 탑승자 시작 흐름

`draft → requested(TTL) → accepted | declined | expired | withdrawn`

- 운전자가 수락하면 회차를 만들되, 탑승자는 이미 참여한 상태로 둡니다.
- 경로 안내는 수락한 다음에만 시작합니다.
- 차량이 오프라인이면 TTL이 끝날 때 만료로 처리하고, 탑승자에게 "차량 미응답"을 보여줍니다.

### 후보와 재검증

- **후보 부족:** 검증된 후보만 보여주고 개수 0~2와 이유를 표시합니다.
- **지점 이동:** 핀을 놓을 때마다 재검증하고, 결과가 나오기 전에는 확정 버튼을 막습니다.
- **수동 핀:** 검증되지 않은 수동 핀을 허용할지는 열린 결정으로 남깁니다(§4).

### Gleo 3개 action

| action | 인자 | 하는 일 |
|---|---|---|
| `GET_PICKUP_STATUS` | 없음 | 기존과 같음 |
| `REPORT_PICKUP_ARRIVAL` | 없음 | 기존과 같음 |
| `OPEN_PICKUP_SEARCH` | `query` 문자열 | activity를 열어 검색어를 미리 채우는 것까지만 |

- `OPEN_PICKUP_SEARCH`의 callback은 화면이 표시되면 즉시 `success("opened")`로 보냅니다. 검색이 끝나기를 기다리지 않으므로 7초 제한과 분리됩니다.
- Board 상태를 바꾸지 않으므로 실행 취소가 필요 없습니다. 후보 선택, 확정, 초대, 경로 시작은 모두 화면에서 사람이 직접 누르게 합니다.
- `query`는 로그에 남기지 않고 결과 데이터로도 돌려주지 않습니다. 인증은 기존 host attest 경계를 그대로 씁니다.
- 1번의 반론 때문에 3번째 칸은 `ACCEPT_PICKUP_REQUEST`와 경쟁합니다. 어느 쪽으로 할지는 §4의 첫 번째 결정입니다.

## 3. 검증 게이트와 대안 (요구를 축소하지 않음)

| 게이트 | 통과 조건 | 미통과 시 대안 |
|---|---|---|
| G1 내비 POI 검색 | 앱이 검색 결과 좌표를 받는 것을 실제로 확인 | (b) 운전자가 내비에서 직접 검색해 목적지로 설정 → `getDestinationInfo`/`onDestinationInfo`를 검색 기준으로 사용 [사실: 문서에 있음, 실행 안 함] |
| G2 지도 · 좌표 선택 | 지도 임베딩이나 좌표 반환이 확인됨 | 자체 지도 SDK(라이선스 확인 필요) 또는 탑승자 휴대폰 지도에서 조정 |
| G3 주행 중 UX | 플랫폼 제한 문서와 실제 차량 확인 | 정차 중에만 조정·초대, 주행 중에는 음성과 알림만 |
| G4 초대 전송 | 연락처 SDK와 메시지 발송 권한 확인 | 운전자 휴대폰에서 공유 시트로 링크 보내기, 사전 연결 목록 |
| G5 차량 연결 · 알림 | 앱이 꺼져 있을 때 차량 push와 팝업이 실제로 뜸 | 앱이 실행 중일 때만 폴링, 미달이면 만료 |
| G6 Gleo | 스키마 승인 → 자연어 호출 → callback 수신을 실제로 확인 | 화면 버튼으로 같은 기능 제공 |

## 4. 열린 제품 결정

1. Gleo 3번째 칸을 검색에 쓸지, 요청 수락에 쓸지
2. 검증되지 않은 수동 핀을 허용할지, 허용한다면 어떻게 표시할지
3. 요청 TTL과 위치 공유 만료 시간
4. 미참여 상태로 출발한 회차를 몇 분 뒤에 닫을지
5. 차량 연결의 해제·인증 방식과 연결 단위(계정 또는 차량)
6. 탑승자 앱의 형태(웹 또는 네이티브)

## 확인 범위와 한계

- 공식 문서와 로컬 SDK 선언은 보지 않았습니다. Codex가 별도로 검증하고 있습니다.
- `server.mjs`와 UI는 보지 않았습니다.
- 위 설계와 게이트는 모두 제안이며, 실행해서 얻은 증거는 없습니다.
