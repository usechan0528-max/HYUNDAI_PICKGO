**No concrete blocking regression found in the pasted CSS.** I reviewed only the snippet, not the DOM or the repo, so the points below are checks, not confirmed defects.

Non-blocking risks to verify:

1. **`.bottom` sticky needs to be a descendant of the scroll container.** `position:sticky` only works inside the nearest scrolling ancestor. Your footer measurement (bottom 543.93 vs footer 552) suggests the footer may sit outside `.welcome`/`.edit-place`/`.end-confirm`. Confirm `.bottom` is inside the scroller.

2. **`transform` on `main>section` creates a containing block for `position:fixed` descendants.** The `pickup-screen-in` animation doesn't leave a transform after it ends, so this only matters if a fixed overlay, sheet, or toast lives inside a section. Check for `position:fixed` descendants.

3. **`align-items: safe center` needs a modern engine.** An engine without `safe` drops the whole declaration and falls back to `normal`, so the overflow-safe centering is lost there. Low risk for a current Android WebView or Chrome, but worth a note if you target older WebViews.

4. **Cascade ordering is correct as written.** The `max-width:899px` block sets `stretch` after the `max-height:760px` block, so on narrow short screens stretch wins. That matches the stated intent, but it is an ordering dependency, so keep those two blocks in this order if you edit them.

The `flex:1` on the scroll containers only produces scrolling if the parent is a bounded flex column. Your 480×600 QA shows scrolling works, so that path looks fine.
