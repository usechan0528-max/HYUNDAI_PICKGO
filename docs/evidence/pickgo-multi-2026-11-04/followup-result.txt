## 리뷰 결과 (읽기 전용, 도구 미사용)

지정된 수정 사항에서 명백한 깨짐은 찾지 못했습니다. 다만 아래 3건은 회귀이거나 확인이 필요한 동작 변경으로 보입니다. 테스트 파일은 읽지 않았으므로, 5개 테스트가 이 경우를 다루지 않는다는 판단은 추정입니다.

### 1. 빠른 연속 클릭이 버전 충돌로 실패 (동작 변경, 확인 필요)
- `run()`은 **스케줄 시점**에 `structuredClone(state)`를 찍습니다. 같은 행동을 두 번 누르면(예: 준비 → 준비 취소) 두 번째 스냅샷도 첫 응답 전의 `version`을 가집니다.
- 첫 `act`가 끝나 서버 버전이 올라가도 두 번째 요청은 옛 `version`을 보내므로 충돌로 거절됩니다.
- 버튼이 `busy` 중에도 비활성화되지 않아 이 경로는 실제로 도달 가능합니다.
- "사용자가 본 상태 기준"이라는 의도라면 맞는 동작이지만, 정상 클릭이 실패하는 것은 사용자에게 보이는 변화입니다.
- 권장: `busy` 중 액션 버튼을 비활성화하거나, 충돌 시 `refresh()` 후 재렌더링.

### 2. 취소 확인 창이 실패 후 고착될 수 있음
- `pendingCancel.snapshot`은 대화상자를 열 때 한 번만 찍힙니다.
- `confirmCancel`이 실패하면 대화상자가 열린 채 남고, 폴링은 `!$('confirm').open` 조건 때문에 멈춥니다.
- 확인을 다시 눌러도 같은 오래된 버전으로 계속 실패합니다. "유지" 후 다시 열어야 벗어날 수 있습니다.
- 권장: 실패 시 대화상자를 닫고 `refresh()`하거나, 재시도 때 스냅샷을 새로 찍기.

### 3. 참여 시작 시 저장 실패가 참여 자체를 막음
- `join`의 첫 줄 `sessionStorage.setItem('pickgo-multi-join', …)`은 try 바깥에 있습니다. 저장소가 쓰기 불가한 환경에서는 예외가 나서 `api` 호출 전에 중단되므로 **새 초대도 참여할 수 없습니다.**
- 초기화 주석("durable retry storage can be written"일 때 새 초대가 동작)과도 맞지 않습니다.
- 의도가 "저장 불가면 참여 거부"라면 주석을 고치고, 아니라면 이 `setItem`을 try로 감싸세요.

### 4. 서버 의존 항목 (클라이언트만으로 검증 불가)
- 저장 실패 후 새로고침 시 같은 `joinId`로 재참여가 되려면, 서버가 **이미 소비된 초대**에서도 같은 `joinId`에 대해 같은 세션을 반환해야 합니다.
- "5분 이내" 안내는 클라이언트가 강제하지 않습니다. 서버 만료 시간과 일치하는지 확인하세요.

### 검토했으나 문제 없음
- `move`의 인덱스 `i`와 `snapshot.order`: 렌더와 상태가 같은 버전에서 갱신되므로 일관적입니다.
- `apply`의 `s.recommendation.id`: 추천이 없으면 버튼이 숨겨져 도달하지 않습니다.
- `run()`의 오류 처리: catch가 큐 체인을 끊지 않습니다.
