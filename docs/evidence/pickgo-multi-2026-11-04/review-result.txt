## 결론: P1 없음, P2 2건

서버 측 `board.mjs`의 권한, 상태 변경, 추천 비동기 검증은 읽은 범위에서 명확한 결함이 없었습니다. 실제 결함은 클라이언트 `page.mjs`에 있습니다. 도구는 사용하지 않았고 테스트도 실행하지 않았습니다. 아래는 코드 읽기만으로 판단한 결과입니다.

### P2-1. 큐 실행 시점에 `state`를 읽어 낙관적 동시성 검사가 우회됨

- **위치**: `page.mjs`의 `command()`, `act()`, `render()` 내부 `move()`, `apply` 핸들러
- **문제**: `button()`은 `run(fn)`으로 작업을 큐에 넣고, `fn`은 큐에서 실행될 때 평가됩니다. 그런데 `command()`는 `state.version`과 `state.view`를 실행 시점에 읽습니다. 따라서 화면을 그린 뒤 폴링(5초)으로 `state`가 갱신되어도, 사용자가 누른 버튼은 최신 `version`과 `view`로 전송되어 서버의 `guard`를 통과합니다.
  - 실제 영향 1: `move(offset)`은 렌더 시점의 인덱스 `i`를 캡처하고 실행 시점의 `state.order`를 씁니다. 그 사이 순서가 바뀌었다면 엉뚱한 지점이 교환되며, 서버는 이를 거부하지 않습니다.
  - 실제 영향 2: `apply`는 `state.recommendation.id`를 실행 시점에 읽습니다. 사용자가 본 추천과 다른 추천이 적용될 수 있습니다.
- **수정 방향**: 클릭 시점에 `version`, `view`, `recommendation.id`, 그리고 대상 `order`를 캡처해 `act`에 넘기십시오. `command()`는 인자로 받은 값을 쓰도록 바꾸면 됩니다.
- **검증 테스트 제안**: 렌더 후 서버 상태를 한 번 바꾸고 "위로"를 눌렀을 때 409가 나오는지 확인하십시오. 현재 구현에서는 409가 나지 않을 것으로 보입니다.

### P2-2. 참여 복구 경로에서 세션 저장 실패 시 1회용 초대를 잃을 수 있음

- **위치**: `page.mjs`의 `$('join').onclick`
- **문제**: 서버 `join`은 초대를 소진시킨 뒤 응답합니다. 클라이언트는 응답을 받은 후 `sessionStorage.setItem(storage, …)`를 직접 호출하는데, 이 호출은 `save()`와 달리 `try/catch`가 없습니다. 쿼타 초과나 저장 차단 환경에서 여기서 throw되면 `session = joined`에 도달하지 못합니다. 결과적으로 메모리 세션도 없고, `pickgo-multi-join` 키만 남습니다.
  - 복구는 같은 `joinId`로 `join`을 다시 호출하는 방식뿐이며, 서버 `receipt`는 5분만 유효합니다. 5분이 지나면 rider 자격 증명을 복구할 수 없습니다.
  - 한편 `join` 키는 먼저 쓰는 구조라 응답 유실에는 잘 대응합니다. 문제는 응답 후 저장 단계입니다.
- **수정 방향**: `session = joined`를 먼저 대입하고 저장은 `save()`를 재사용해 실패 시 경고 메시지만 띄우십시오. `pickgo-multi-join` 키는 세션 저장이 성공했을 때만 지우십시오.
- **검증 테스트 제안**: `sessionStorage.setItem`을 두 번째 호출에서 throw하도록 스텁하고, 복구 후 `session`이 유지되는지 확인하십시오.

### 확인했으나 결함으로 보지 않은 항목

- **사람별 접근 권한**: 탑승자는 `ready`, `board`, `cancel`만 허용되며, 대상은 `actor.p`로 고정되고 `participantId`가 다르면 403입니다. `read`의 rider 응답은 본인 지점만 노출합니다.
- **추천 비동기 경쟁**: `recommend`는 `version`과 `calculation` 세대 값을 함께 검사하고, `act`는 `touch`로 `version`을 올리므로 계산 중 변경은 409로 걸러집니다. 동시에 두 번 추천해도 이전 결과는 세대 불일치로 버려집니다.
- **`apply` 검증**: 적용 전 `touch`로 추천이 무효화되고, 서버는 `id`, `version`, 만료 시각을 모두 확인합니다.
- **`planner.mjs`**: 최대 6개 지점의 전수 탐색은 허용 범위이며, 모든 쌍의 행렬 값이 없으면 `ROUTE_MISSING`으로 실패합니다.
- **`join` 재시도 응답**: 같은 `joinId`로 5분 안에 다시 호출하면 기존 `credential`을 돌려줍니다. 초대 토큰만으로는 `joinId`를 알 수 없으므로 자격 증명이 유출되지 않습니다.

### 참고

- P2-1은 테스트가 없다면 회귀를 잡기 어렵습니다. 위의 검증 테스트 제안을 추가하는 것을 권장합니다.
