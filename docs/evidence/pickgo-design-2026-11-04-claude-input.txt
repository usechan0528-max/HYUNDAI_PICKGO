목적: 사용자 요청에 따른 PICKGO 세부 설계 공동 검토. 소스 수정 없는 독립 기획 검토. 모델 claude-opus-5-5. J-01 폐기 유지.
입력 범위: docs/PICKGO_USER_FLOW_2026-11-04.md 전체, experiments/pickup-board/gleo/README.md, 필요시 experiments/pickup-board/domain.mjs의 상태 전이. 다른 문서/전체 이력 조사 또는 파일 수정 금지. 현재 main 미커밋 변경은 다른 작업자 소유이며 건드리지 말 것.
사용자 핵심: 운전자 현대 내비 장소검색(음성/직접/Gleo)→근처 적격 3후보→지도 세부조정→사람 선택·초대링크→내비 안내+대상 위치. 대상은 링크로 위치공유·장소제안. 탑승자 앱에서도 사전 연결 차량에 같은 장소선정 후 요청, 차량 팝업 알림.
Codex가 오늘 공식 문서에서 확인한 사실(실행 아님): NaviHelper3.0.5는 requestRoute(RouteInfo), getDestinationInfo, onDestinationInfo, Navigation 화면 요청, 탐색 이벤트 제공. 아직 POI 검색결과 반환·내장 지도 임베딩·좌표 선택 반환 계약은 미확인. Gleo 최대3 action, activity/startActivity 또는 service/sendBroadcast, success/asking/fail과7초 timeout, assets/schema.json 검토승인 필요. STT는 텍스트 변환만 제공하며 검색엔진 아님. 기존Gleo 준비는 GET_PICKUP_STATUS와 REPORT_PICKUP_ARRIVAL 두 개, native 실제연동 없음.
검수 질문: (1) 두 진입 흐름을 상태·화면·권한·동의 관점으로 구체화하고 운전자 수락/초대미참여/장소제안경쟁/내비재탐색 실패/후보부족/지점이동 재검증을 어떻게 처리할지 (2) Gleo3개 action 안에서 신규 검색을 기존2개와 함께 구성하되 인증/7초/실행취소 경계를 어떻게 설계할지 (3) 사용자 요구를 축소하지 않으면서 미확인 내비POI검색·지도·모바일 차량연결·전송 기능을 어떤 검증 게이트와 대안으로 나눌지.
제안 초안: 검색기준장소와 확정승차좌표 분리, 지점 revision 기반 제안/수락, 내비 상태는 별도, GPS로 합의지점 자동변경 금지, 탑승자 요청은 운전자 명시수락 후 경로 시작, 운전자 초대는 전송실패/전달/참여 구분, 미참여중 운전자 명시출발 가능. 적격3개 미만이면 확인된 수만. 연속 위치는 회차별 동의·철회·만료·stale 표시. 초대 대상은 사전연결 목록 우선 제안(연락처 SDK 가능성 미확인). 통신서버와 모바일 제품은 별도 필요. 외부플랫폼 지원/인증/자동발송 권한 추정 금지.
기대 출력: 주요 결함/반론→보완된 설계→수용조건→열린 제품결정. 사실/제안 구분, 1500자~2500자 정도. 다른 에이전트 재위임/코드구현/외부발송 금지. Codex가 공식API와 실제 로컬SDK 선언을 별도 검증 중이다.
