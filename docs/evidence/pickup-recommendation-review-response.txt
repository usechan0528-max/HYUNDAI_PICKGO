**Scope:** Read-only review of the pasted snapshot. I used no tools, changed no files, and ran nothing. Findings come from reading the code.

## Findings

**F1 · P1 · Privacy / fail-closed: default provider accepts real rider GPS**
- Evidence: `providers.mjs` sets `unavailableProvider.mode='live'`. `board.mjs` `grant` has no provider check. `publish` gates only with `this.provider.mode==='synthetic'||role==='rider'`, so a rider's `browser-geolocation` fix is accepted under the default provider. `server.mjs` main entry uses `new RecommendationBoard()`, which is that default.
- Impact: Any authenticated rider (a crafted client or curl) can store real coordinates for about 15 s and create grants, despite "default unavailable, no actual location captured." UI gating is not sufficient. Every test uses the synthetic provider, so nothing catches this.
- Minimal fix: At the top of `grant` and `publish`, add `check(this.provider!==unavailableProvider,409,'추천 위치 기능이 연결되지 않았습니다.')`. Rename the unavailable mode to `'unavailable'` so `status.mode` is not misleading. Add a test: default board, grant and publish both return 409, and `p.fix` stays null.

**F2 · P2 · Proposal has no effective TTL**
- Evidence: `select` stores `until:s.until` in `e.proposal`, but nothing reads it. `sweep` never clears proposals.
- Impact: A recommendation proposal stays pending until accepted, rejected, or withdrawn, even after its grants lapse. Accept is still safe because it re-evaluates, but the UI shows a stale pending proposal.
- Minimal fix: In `sweep`, clear `e.proposal` when `at>=e.proposal.until` or when either grant is null. Check the same in `accept`.

**F3 · P2 · Spurious accept failure from the view TTL**
- Evidence: Views live `VIEW_TTL=8000`. The accept path re-runs `this.context()` after a provider wait of up to 3 s, and the page allows `run` at about 6 s of view age.
- Impact: A slow provider can make a valid accept fail with "최신 회차를 다시 확인해 주세요." This fails closed but is confusing.
- Minimal fix: Keep the post-await version and revision CAS, which is the real guard. Remove the second `context()` call, or re-read a view.

**F4 · P2 · Evidence freshness is not bounded**
- Evidence: `engine.mjs` checks `checkedAt<=wall` and `validUntil` only. Old `checkedAt` with a future `validUntil` passes.
- Impact: This conflicts with the "fresh, evidenced" requirement.
- Minimal fix: Add `wall-e.checkedAt <= POLICY.evidenceMaxAgeMs` and set the value per source as a product decision.

**F5 · P2 · Accepting party sees no evidence**
- Evidence: `state.proposal` contains only the place name. The stored `e.proposal` holds only `candidateId`.
- Impact: The counterpart accepts a place without seeing the reason, `checkedAt`, or `validUntil`.
- Minimal fix: Store the proposer's displayed summary in `e.proposal` and render it in the proposal section. The server should still re-evaluate on accept.

**F6 · P2 · Touch and render usability (`page.mjs`)**
- Evidence: `show()` runs on every 2 s refresh and calls `replaceChildren()`. `notify` sets `result=null` on every successful publish, about every 8 s in synthetic mode and about once per second on real GPS.
- Impact: On touch, a candidate button can be removed between pointerdown and click, losing the tap. Calculate and select are disabled until the next refresh, and the status message is overwritten.
- Minimal fix: In `show`, rebuild candidates only when `data.snapshot?.id` changes. Remove `result=null` from `notify`.

**F7 · P2 · Newest GPS fix is dropped while busy (`controller.mjs`)**
- Evidence: `publish` returns early when `c.busy`, so the freshest fix is discarded and the older in-flight fix is what the server keeps.
- Impact: The message "최신 위치만 사용합니다" is false.
- Minimal fix: Keep a single pending slot holding the latest fix, and send it when the current request completes.

**F8 · P2 · Test gaps and one misleading test**
- "expired proposed recommendation is not accepted" calls `x.b.act`, which is the refusal path. It never exercises expired acceptance through `recommend`. Expiry currently works only because the synthetic route's 5 s `until` lapses.
- Missing coverage: default-provider privacy (F1), the 100-entry `used` cap fail-closed behavior, the 3 s provider timeout, a counterpart withdrawing during an in-flight accept, and evidence staleness (F4).

## Verified in code

- Accept through `/actions` is refused only when `e.proposal` matches `r.proposal`. Other manual proposals are unaffected. The proposer cannot accept their own proposal (`by!==role`).
- CAS is sound: version and revision are checked after the provider await. The `busy` guard prevents concurrent calculations. The timeout is cleared in `finally`, and a provider throw maps to `provider-unavailable`.
- Memory is bounded: `used` is capped at 100 per role and fails closed. Fixes and snapshots are swept every second. Entries are deleted with their rooms.
- Clock: a monotonic rollback clears grants and fixes. Freshness uses the monotonic clock. Wall time is used only for evidence.
- Revoke removes the grant, and accept requires both grants.
- Candidate output contains no coordinates.

## Limitations

- Both parties' coordinates are self-reported. `ageMs` is client-asserted, so the server proves only receipt time. Two-party consent does not stop spoofing. The counterpart's acceptance is the only mitigation.
- `crypto.randomUUID` requires a secure context. Access over LAN HTTP will break the page.
- Only the synthetic path is in scope. Live routing, curb data, the catalog, and the native SDK are blocked by design and were not reviewed.
- The test summary reports 146 pass and 0 fail. The referenced tests-final file was not in the input, so I could not verify per-file counts.
- Browser behavior was not verified.
