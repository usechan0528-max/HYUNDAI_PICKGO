## 결론

고정 스냅샷 기준으로 **P0(잘못된 목적지 발신·중복 발신)은 찾지 못했습니다.** 발신 전 영구 기록, 발신 전 서버 재검증, 목적지와 `ROUTE_GUIDING` 기반 성공 판정은 코드에 구현되어 있습니다. 다만 **P1 3건**이 있습니다. 세 건 모두 사용자에게 보이는 결과 메시지를 잘못 표시하는 문제이며, 수정 범위는 `NavigationActivity.java` 한 파일로 작습니다.

이 검토는 제공된 코드만 읽은 텍스트 리뷰입니다. 파일은 수정하지 않았고 명령도 실행하지 않았습니다.

## P1

**P1-1. 45초 관찰 종료 후 결과 메시지가 덮어써짐**
- 위치: `NavigationActivity.tick()` → `refresh()` 콜백
- 근거: `tick()`에서 `sent=false`로 바꾼 뒤 같은 틱에서 `refresh()`를 호출합니다. 그러면 `refresh` 콜백이 `message("이 확정 지점은 이미 안내 요청했습니다…")`를 설정해 "시간 초과" 문구와 "안내 확인" 문구를 지웁니다. 실제로 사용자가 보는 것은 시간 초과나 확인 결과가 아니라 "이미 요청했습니다"입니다.
- 최소 수정: 결과 문구를 `outcome` 필드에 보관하고, `outcome != null`이면 `refresh()`를 건너뜁니다.
```java
private String outcome; // verified/timeout에서 설정, begin()과 onPageStarted에서 null로 초기화
// verified(): message(outcome="현대 내비 안내 확인 · …");
// timeout:    outcome="안내 확인 시간 초과 · …"; message(outcome);
// tick():     if(resumed && !starting && !sent && outcome==null) refresh();
```

**P1-2. 발신 후 웹 회차 변경·취소를 감지하지 않음**
- 위치: `tick()`의 `sent` 구간, `verified()`
- 근거: 발신 뒤 45초 동안은 SDK 조회만 하고 서버 권한은 다시 읽지 않습니다. 그래서 상대가 제안하거나 취소해도 `verified()`는 계속 "확정 지점과 목적지가 일치합니다"를 표시할 수 있습니다. `onPageStarted`로 페이지가 바뀌어도 `sent`는 유지되고 `verified()`에는 회차 검사가 없습니다.
- 자동 취소 여부에 대한 판단: **자동 취소하지 않는 것이 맞습니다.** SDK 취소 경로가 검증되지 않았고, 운전자가 이미 확인 중인 경로를 앱이 바꾸면 위험합니다. 대신 **경고**는 해야 합니다.
- 최소 수정: `sent` 동안 약 3초마다 `readTarget()`을 호출합니다. `RouteGate.same(requested, t)`가 깨지거나 읽기가 실패하면 `roundIntact=false`로 바꾸고, 메시지는 "웹 회차가 바뀌었습니다. 현대 내비 경로는 자동 취소하지 않았으니 현대 내비에서 확인하세요."로 씁니다. `verified()`는 `roundIntact`가 true일 때만 성공을 표시합니다.

**P1-3. 성공 판정이 한 번 설정되면 되돌아가지 않음**
- 위치: `verified()`
- 근거: `verified()`는 조건이 맞을 때만 메시지를 설정하고, 조건이 깨져도 이전 "확인" 문구를 지우지 않습니다. `guiding`이 `false`로 바뀌어도 문구는 남습니다. P1-1과 합치면 확인 문구는 최대 45초 동안 남거나 시간 초과 시 덮어써집니다.
- 최소 수정: `else`에서 `message("현대 내비 상태를 확인 중입니다…")`로 되돌립니다. P1-1의 `outcome`과 함께 적용합니다.

## P2

1. **`readTarget()`의 4초 예산이 실제로 강제되지 않음** (`readTarget`). `getResponseCode()`는 연결 2.5초와 읽기 2.5초가 걸릴 수 있고, 본문 루프는 각 읽기 뒤에만 시간을 확인합니다. 최악의 경우 약 7.5초까지 걸립니다. 각 단계 전에 `max(1, 4000-(now()-began))`으로 타임아웃을 다시 설정하면 됩니다.
2. **`proposal` 키가 없으면 제안 없음으로 통과함** (`readTarget`). `!r.isNull("proposal")`는 키가 없어도 `false`를 반환합니다. `!r.has("proposal") || !r.isNull("proposal")`로 바꾸면 "제안중 차단"이 실패 쪽으로 닫힙니다.
3. **성공 문구가 요청의 결과라고 단정함.** `ROUTE_GUIDING`과 목적지 일치는 현재 상태입니다. 이전부터 같은 좌표로 안내 중이었다면 이 요청이 시작시킨 것이 아니어도 성공으로 보입니다. 요구된 판정 방식 안에서는 허용 가능하지만, 문구는 "현재 내비가 확정 지점으로 안내 중입니다"처럼 상태를 말하도록 바꾸는 것이 맞습니다.
4. **버튼 문구가 실제 동작보다 강함.** "확정 지점으로 현대 내비 안내 시작"이라고 쓰지만 실제 최종 시작은 차량 화면에서 눌러야 합니다. "현대 내비에 경로 요청"으로 바꾸는 편이 맞습니다.
5. **`connected=false`가 복구되지 않음** (`tick` catch, `initialize` 실패 콜백). 한 번 끊기면 앱을 다시 열기 전까지 버튼이 계속 비활성입니다. 재초기화 또는 재시도 안내가 필요합니다.
6. **`new NaviHelper(this)`가 try 밖에 있음** (`onCreate`). 생성자가 던지면 앱이 바로 종료됩니다. try 안으로 옮기는 것이 좋습니다.
7. **새 회차는 45초 뒤 발신 가능.** 이전 경로가 차량 화면에서 아직 확인 대기 중이어도 새 요청이 기존 경로를 덮어쓸 수 있습니다. 발신 전에 "이전 경로가 대기 중일 수 있음"을 표시하는 것이 안전합니다.
8. **`commit()`이 메인 스레드에서 동기 디스크 쓰기를 함** (`begin`). 중복 차단 정확성에는 필요한 선택이므로 유지해도 됩니다. 다만 StrictMode나 ANR 가능성은 알고 있어야 합니다.
9. **화면 회전이나 재생성 중 관찰이 조용히 끝남** (`onDestroy`, `sent` 상태 소실). `used`가 남아 중복은 막히지만 사용자에게 알림이 없습니다.
10. **`io.shutdownNow()`는 `HttpURLConnection`을 중단하지 않음** (`onDestroy`). 소켓은 타임아웃까지 남습니다. `c`를 필드로 보관해 `onDestroy`에서 `disconnect()`를 호출하면 됩니다.
11. **`usesCleartextTraffic="true"`가 앱 전체에 적용됨** (`AndroidManifest.xml`). 데모용이면 `network_security_config`로 `127.0.0.1`만 허용하는 편이 좋습니다.
12. **`RouteGateTest`는 순수 정책만 검증함.** `begin`, 중복 차단, 시간 초과, 연결 실패 흐름은 자동 테스트가 없습니다. 결과 결정을 순수 함수로 분리하면 테스트할 수 있습니다.

## 질문별 판단

- **서버 권한 읽기와 IPC 사이의 원자성:** 물리적으로 보장할 수 없습니다. 현재 창은 `observed`가 읽기 시작 시각이라 보수적이고, 메인 스레드 재확인 뒤 바로 IPC를 호출합니다. 따라서 문구를 "요청 시점 기준 확인"으로 두고, P1-2의 상시 감시로 이후 변경을 보여주는 것이 현실적입니다.
- **네트워크 작업 취소와 생명주기:** `onPause`와 `onDestroy` 뒤의 콜백은 `destroyed`와 `gen` 검사로 버려집니다. 소켓 정리만 P2-10처럼 보강하면 됩니다.
- **SDKonError:** 현재 처리는 "확인 바람" 문구만 표시하고 `sent`를 바꾸지 않습니다. 의미가 확정되지 않았으므로 이 방식이 맞습니다.
- **발신 전 영구 기록:** 설계상 의도입니다. 명시적 예외는 불확실 발신으로 간주되어 막히는 것이 맞습니다. 다만 발신 전에 확실히 실패한 경우에도 같은 회차가 막히므로 새 회차 안내가 필요합니다.

## 수용조건 대조

| 조건 | 코드상 상태 |
|---|---|
| 제안중 | 구현됨. 키 누락 시 통과(P2-2) |
| 취소/종료 | 시작 전 검사는 구현됨. 대기 중 감지 없음(P1-2) |
| 오래된 선택 | `fresh` 8초와 `same()` 구현됨 |
| 중복 | 발신 전 영구 기록으로 구현됨 |
| 원점 | `local()`, 고정 ORIGIN, 리다이렉트 차단으로 구현됨 |
| 입력 검증 | 정규식과 `validate()`로 구현됨 |
| 연결 실패 | 부분 구현. 복구 없음(P2-5) |
| 시간 초과 | 4초 예산 미강제(P2-1). 45초 뒤 문구 덮어쓰기(P1-1) |
| 목적지 + `ROUTE_GUIDING` 판정 | 구현됨. 래치와 문구 문제(P1-3, P2-3) |
| 호출 반환만으로 성공 금지 | 구현됨. `requestRoute` 반환은 "요청했습니다"만 표시 |

이 검토는 코드 읽기 기준입니다. 실제 SDK 동작, `CarUxRestrictions`, 실차, HTTPS, 실제 폰은 검증되지 않았습니다. P1-1은 코드 흐름만으로 확정할 수 있고, 한 번 에뮬레이터에서 45초 뒤 로그와 화면을 확인하면 바로 검증할 수 있습니다.
