## PICKGO 후속검수 결과

plan 모드라 파일 수정이나 도구 실행 없이 입력 텍스트만 검토했습니다. 새 P0는 없고, 새 P1이 1건 있습니다.

### 이전 P1 3건

1. **45초 결과 덮어쓰기: 부분 수정.** `tick()`의 종료 분기가 outcome을 저장하고 `sent=false`로 바꿉니다. 이후 늦게 도착한 SDK 콜백과 `checkRound` 결과는 `!sent` 가드에서 버려집니다. 단, 아래 R1의 경로에서는 종료 결과가 다시 덮어써집니다.
2. **발신 후 회차 변경 미감지: 수정 확인.** `checkRound()`가 약 3초마다 `readTarget`으로 재검증합니다. 조회 실패, proposal 존재, stage 변경은 `validate` 예외를 거쳐 `roundIntact=false`가 되고 `ROUND_UNAVAILABLE`이 표시됩니다. 자동 취소는 없고 안내 문구도 유지됩니다.
3. **성공 표시 래치: 수정 확인.** `verified()`는 호출될 때마다 `observation()`을 다시 계산합니다. `confirmed()`는 3초 창의 시간 기준이므로 모드 상실, 목적지 불일치, 오래된 데이터가 생기면 `WAITING`으로 내려갑니다. 순수 테스트도 이 경우들을 다룹니다.

### 새 P1 (R1): 종료 결과가 `refresh()`에 의해 덮어써짐

- `tick()`에서 45초 종료 직후 같은 tick 안에 `refresh()`가 호출됩니다(`resumed && !starting && !sent`).
- `refresh()` 콜백의 실패 분기 두 곳은 `used(key)`를 확인하지 않고 메시지를 바꿉니다.
  - sessionStorage 값이 null이거나 세션이 아니면 `JSONException`이 catch되어 "지도에서 픽업 지점을 확정하고 상대를 초대하세요."가 표시됩니다.
  - `readTarget` 실패 catch는 "지도 지점·상대 참여·장소 합의를 확인하세요…"를 표시합니다.
- 두 경우 모두 `outcome`은 prefs에 저장되어 있지만 화면에서는 1.5초 안에 사라집니다. 이것은 "45초 결과 덮어쓰기" P1의 재발입니다.
- 발생 조건은 종료 후 세션 storage가 비거나 방 조회가 실패하는 경우입니다. 입력에 세션 유지 방식이 없어 실제 빈도는 미확인입니다.
- 최소 수정 방향(이번 검수에서는 수정하지 않음): `refresh()` 실패 분기에서 `requested!=null && used(requested)`이면 저장된 outcome을 유지하고 return합니다.

### P2 잔여

- **R2 (LAST_GUIDING 영속):** 종료 시점 확인이 "최근 확인: … 안내 중"으로 저장되어 재시작 후에도 표시됩니다. 라벨이 있어 완화되지만, 성공 문구가 오래 남습니다. "45초 관찰 종료 시점 확인"처럼 시점을 문구에 명시하는 편이 안전합니다.
- **R3 (version 미비교):** `RouteGate.samePlace`는 version을 비교하지 않습니다. 같은 revision 안에서 version만 바뀌면 회차 변경으로 잡히지 않습니다. 서버에서 revision이 회차 식별자라면 의도된 설계로 보이므로 주석으로 근거를 남기면 됩니다.
- **매니페스트 연결 미확인:** `network_security_config.xml`의 설정은 맞습니다(base `cleartextTrafficPermitted=false`, 127.0.0.1만 허용, `includeSubdomains=false`). 다만 `AndroidManifest.xml`에 `android:networkSecurityConfig`가 연결되어 있는지는 입력에 없어 확인되지 않았습니다.

### 회귀 없음으로 확인한 항목

- `RouteGate`의 `validate`, `matches`, `observation` 호출부는 인자 순서(lon/lat, lat/lon)가 일치합니다.
- `RouteGateTest`의 기대값은 `observation` 로직과 맞습니다. 예를 들어 `now-destinationAt=3000`은 `<3000`에서 false가 되는 경계까지 맞습니다.
- `proposal` 키가 없으면 fail-closed로 거부됩니다.
- 재발송 방지는 `used(key)`를 `commit()`으로 먼저 기록한 뒤 발신하는 순서입니다.
- `begin()`의 재검증 가드(generation, resumed, home, connected, fresh, same, used)는 유지됩니다.
- 외부 origin 차단(`shouldOverrideUrlLoading`, `shouldInterceptRequest`)은 그대로입니다.
- read deadline, 생성자 try 내부 처리, 재실행 관찰중단 안내는 코드에 반영되어 있습니다.

### 검증 한계

- 입력은 정적 텍스트뿐이어서 빌드, `RouteGateTest` 실행, 43개 정책 시험 로그는 확인하지 못했습니다. 입력에 없는 결과는 통과로 판단하지 않았습니다.
- 기기 증거는 두 번째 정상경로 1건입니다. 연결단절 캡처는 조작 혼입으로 판정 유보되어 있습니다.
- 실차, CarUxRestrictions, 물리 폰, HTTPS는 미검증입니다.
- 실패 9항목은 첫 검수 전 구현에서 실행한 결과이므로 현재 코드의 회귀 근거로 쓸 수 없습니다.
- 자동 재연결은 재실행 안내로 제한되어 있고, 발신 후 취소는 경고만 하며 내비를 자동 취소하지 않습니다. 이 방침은 입력과 코드가 일치합니다.
