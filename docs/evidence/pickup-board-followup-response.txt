## 판정

읽기 전용 검토 결과, 이전 지적사항(P1 stale 문구, P2 행위자 모호성·철회 누락, P3 응답 시점 신선도)은 코드상 대부분 닫혔습니다. **P0/P1은 코드 읽기 기준으로 확인되지 않았습니다.** 아래 P2 한 건은 로컬 시연 범위에서는 수용 가능하지만, 다음 수정 때 함께 고치는 것을 권합니다. 브라우저 동작 자체는 제가 재현하지 않았고, 제시된 테스트 출력(11/11 통과)과 코드 독해로만 판단했습니다.

## 확인된 수정

- **신선도 판정**: `adopt`에서 `requestTimes`로 요청 시작 시각을 기록하므로 `received`는 서버 `read` 시각보다 이릅니다. 클라이언트 6초 창이 서버 `VIEW_TTL` 8초보다 짧아 보수적입니다. 늦게 도착한 같은 버전 응답이 `>=` 조건으로 채택되어도 `received`가 더 이르게 잡히므로 안전 방향입니다.
- **stale 상태의 쓰기 차단**: `act`는 `fresh()`를 확인하고, `render`는 `can`으로 준비/제안/수락/거절/철회/종료 버튼을 모두 비활성화합니다. `confirmEnd`도 `can`으로 막힙니다.
- **행위자 중립화**: 이벤트 문구("장소 변경을 제안했습니다", "이번 픽업 약속을 종료했습니다")는 특정 역할을 가리키지 않습니다.
- **철회 권한**: 도메인은 `proposal.by === role`만 허용하고, UI는 `own`일 때만 철회 버튼을 보여 주며 수락/거절 영역은 숨깁니다. 테스트 `withdraw belongs to proposer`가 이를 검증합니다.
- **stale 문구**: 제목은 "다시 확인해 주세요", 장소 라벨은 "현재 미확인", 준비 상태는 "현재 미확인", 제안 문구와 이벤트 접두어도 모두 미확인을 명시합니다.
- **서버 방어선**: 요청 크기, JSON 타입, Host/Origin, 1회용 초대, 교차 방 자격 증명, `requestId` 중복, 뷰 리스 위조 차단이 테스트로 확인됩니다.

## 남은 이슈

**P0: 없음**

**P1: 없음**

**P2-1. `unavailable` 플래그가 성공 후 초기화되지 않음** (`app.mjs`, `adopt`/`refresh`)
- `unavailable`은 실패 시에만 `true`가 되고 `adopt`에서 다시 `false`로 돌아가지 않습니다.
- 결과: 401/403/404가 한 번이라도 나면 활성 회차 중에도 "새 약속 시작" 버튼이 계속 보입니다. 운전자가 이 버튼을 누르면 sessionStorage가 지워져 진행 중 회차에서 떨어져 나가고, 상대는 회차에 남습니다. 파괴적 서버 작업은 아니지만 사용자가 약속을 잃을 수 있습니다.
- 권고: `adopt` 성공 시 `unavailable = false`로 재설정하고, 404만 이 경로로 보내는 것을 검토하십시오.

**P3-1. stale 상태에서 초대 박스가 신선도와 무관하게 표시됨** (`render`, `inviteBox`)
- `inviteBox`는 `valid`를 보지 않습니다. 상대가 이미 참여했더라도 stale 화면에서는 초대 링크가 보일 수 있습니다. 링크 열기는 서버에서 403으로 거부되므로 보안 문제는 아닙니다.

**P3-2. 제목 문구가 "현재 미확인"을 명시하지 않음** (`headline`)
- "현재 약속을 다시 확인해 주세요."는 재확인을 요구하지만, 다른 stale 섹션처럼 미확인 상태를 직접 말하지는 않습니다. 이전 지적의 "모든 stale 섹션에 명시" 요구를 엄격히 보면 미충족입니다.

**P3-3. 방/요청 한도로 인한 자기 서비스 거부**
- 방 100개, 방당 요청 ID 1000개 한도가 있어 한 사용자가 로컬 서버를 막을 수 있습니다. 로컬 시연 범위에서는 수용 가능합니다.

**P3-4. 413 응답 중 요청 본문 소비 중단**
- 과대 본문에서 본문을 끝까지 읽지 않은 채 응답을 보냅니다. 테스트는 통과하지만 클라이언트에 연결 재설정이 나타날 수 있습니다. 로컬 범위에서는 무해합니다.

## 인접 회귀 점검

- 새 회차 시작 직후(`session` 없음 → `board` 표시 → 404) 경로: `new` 버튼이 보이고 `state` 없이도 문구가 깨지지 않습니다.
- 오류 후 `refresh` 실패 시 `online=false`로 모든 쓰기가 막히고, 다음 성공 폴링에서 복구됩니다. 의도된 동작입니다.
- 같은 요청 ID 재시도: 실패한 요청은 `requests`에 기록되지 않고 클라이언트는 매번 새 UUID를 만듭니다. 중복 적용 위험은 없습니다.
- 더블클릭: `busy`가 막습니다. `act`와 `refresh`의 겹침은 서버의 `version` 검사로 안전합니다.
- 종료 후 초대: `end`에서 `invite = null`로 무효화되고 `join`도 `active`를 요구합니다.

## 권고

이번 범위는 **로컬 시연으로 수용 가능**합니다. P2-1은 짧은 수정이므로 다음 커밋에서 `adopt` 시점의 `unavailable` 재설정과 회귀 테스트(404 후 복구 시 새 버튼 숨김)를 추가하는 것을 권합니다. 브라우저 확인 항목은 "활성 회차에서 일시 403 발생 후 새 시작 버튼이 숨겨지는지"입니다.

(참고: 계획 모드이며 편집 없이 답변만 드렸습니다. 계획 파일은 작성하지 않았습니다.)
