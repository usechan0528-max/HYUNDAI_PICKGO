# 제로부터 100개 아이디어 토너먼트 결과

2026-11-02 KST · 담당 Codex · 실제 회의 상대 Claude Opus 5.5 · 공식 반례 조사 Dot 및 Codex

## 선정 결과

**C02 ‘픽업 약속판’을 다음 개발 방향 하나로 선정했다.** 가족·지인을 반복적으로 데리러 가는 사람이, 상대의 준비 상태와 만날 지점 변경을 한 회차 안에서 합의하는 앱이다. 잔여 차별 가설은 **이동 전의 명시적 준비 의사**와 **지점 변경의 제안/수락 구분**이다. 위치·도착·남은거리·지점 공유는 카카오맵 등 기존 기능이므로 차별점으로 계산하지 않는다. 준비·합의 흐름을 결합하고 Gleo로 구조화된 회차 상태를 화면 없이 조회·변경하는 것이 목표다. Gleo 승인·실행이 불가하면 이 조건부 차이도 사라진다.

사용자가 선정까지 위임한 D-018에 따른 상대적 기획 선택이다. 기존 서비스보다 확실히 우월하다는 실측 판정은 아직 아니다. 이 차이는 결론을 미루는 것이 아니라, 선정과 제품 성공의 증거를 구분하는 것이다. 오늘 범위인 50+50 생성·상호 논의·최종 1개 선택은 완료했다. 앱 구현과 실사용 시험은 이번 작업에서 하지 않았다.

선정에서 크게 작용한 것은 우위가 이미 입증됐다는 판단이 아니라, 결선 중 앱이 소유할 합의 상태가 분명하고 외부 ETA·주행계 의존 없이 우위 가설을 빨리 반증할 수 있다는 점이다. 기존 채널로 처리해도 확인 연락·오대기가 남는 변경/준비지연 회차가 드물면 일상 반복 불편 기준을 충족하지 못한다. 결정 규칙은 결선 후보 모두 가치가 미입증일 때, 우위 가설의 검증·중단 판단에 필요한 외부 의존과 비용이 적은 후보를 먼저 시험하는 것이다. 이는 사용자 가치의 대리 증명이 아니다.

## 실제 진행과 감사

- Codex 50개를 파일로 고정한 뒤 Claude 50개 응답을 읽었다. Claude 생성 입력에는 Codex 후보 목록을 넣지 않았다.
- 실제 CLI 모델은 `claude-opus-5-5`. 총 9회 호출(독립 생성 1, 라운드 판정 7, 추가 반론 1)로 토너먼트를 수행했다. 라운드당 단일 호출 일괄 판단으로 경기별 심의 깊이에 한계가 있다. 이후 최종 보고서 검수와 추가 근거 재심은 별도다.
- 후보 생성은 독립했으나 라운드에서는 Claude에게 Codex의 선택과 이유를 전달했다. 맹검 독립 투표가 아닌 상호 검토이며 앵커링 가능성을 배제하지 않는다.
- 100→50→25→13→7→4→2→1, **99경기**. 86경기는 처음부터 의견 일치, 13경기는 이견 발생: Codex가 12회, Claude가 1회 승복했다.
- 초기 C01–L01…C50–L50, 이후 생존 순서의 인접 대진을 유지했다. 홀수 라운드 3·4·5에서 C50이 부전승했다. 균등 추첨이나 전 후보 조합의 최적 순위를 보장하지 않는 고정 대진이다. C50은 4강에서 탈락했다.
- 100개는 원본 제출 수다. 유사한 문제와 변형도 포함하며 100개 시장독창성 주장이나 전 세계 앱 전수조사 완료를 뜻하지 않는다.

## 앱이 실제로 해결하려는 장면

우선 대상은 스마트폰으로 직접 응답할 수 있는 가족·지인을 반복 픽업하는 운전자다. 어린아이의 학교 인계·보호자 권한 확인 서비스로 넓히지 않는다. 대상의 크기와 사용 빈도는 아직 조사하지 않았다.

1. 운행 전, 운전자와 상대가 이번 픽업 회차 및 만날 지점을 정한다. 이 단계 자체는 기존 지도 공유와 동일한 기본 흐름이며 차별 기능이 아니다. 상대는 공유받은 링크 또는 폰 화면에서 참여한다. 링크 열기·인증 비용도 제품 부담이다.
2. 상대는 이동을 시작하기 전 ‘준비됨/아직 준비 중’을 명시한다. 이동 후 위치나 남은거리만으로 충분히 상태를 알 수 있는 경우까지 차별로 계산하지 않는다. 운전자는 Gleo에 “이번 픽업 준비됐어?”라고 물어 이 회차의 최신 확인 상태를 듣는 흐름을 목표로 한다.
3. 지점을 바꿔야 하면 ‘2번 출구로 변경 제안’을 보낸다. **제안을 보낸 상태와 상대가 수락한 상태를 구별**한다. 수락 전에는 기존 합의를 조용히 덮어쓰지 않는다.
4. 만난 뒤 회차를 종료한다. 응답 없음·연결 끊김·오래된 상태는 미확인으로 남긴다. 앱의 종료 버튼을 실제 안전한 탑승 확인으로 해석하지 않는다.

상대방이 수시로 위치를 방송하는 대신, 이번 만남에 필요한 명시 상태를 공유하는 범위다. 위치 추적·정확한 ETA·자동 문자 읽기/송신을 핵심 성립 조건으로 넣지 않는다. 주정차 가능 여부를 보증하거나 위험한 위치로 안내하는 기능도 아니다. 웹 백그라운드 알림이 항상 전달된다고 가정하지 않는다. 변경을 제때 인지하지 못하면 전화/메신저가 추가로 필요해지고, 이 비용도 실패 지표에 포함한다.

## Gleo와 공존하는 이유와 한계

| 역할 | 담당 |
|---|---|
| 발화 이해와 앱 기능 호출, 결과 전달 | Gleo 연동 목표 |
| 회차별 참여자·준비상태·현재 합의지점·미수락 제안·변경 이력·종료 상태 | 앱과 자체 서비스 |
| 상대의 준비·수락 의사 | 상대의 명시 입력 |

Gleo가 전화·메시지·내비 기능을 제공한다는 사실과, 이 앱의 양측 합의 상태를 기본으로 관리한다는 것은 다르다. [현대 Gleo 설명서](https://ownersmanual.hyundai.com/ivi/Connect-S/AVNT/KOR/Korean/003_Corefeatures_1.html)에서 후자의 전체 흐름은 확인하지 못했다. ‘Gleo가 절대로 만들 수 없다’는 독점성 주장은 하지 않는다. 선택 논리는 현재 앱이 실제 공유 상태를 소유하고 Gleo가 이를 이용하도록 만드는 것이다.

공식 [Schema 전달 가이드](https://document.pleos.ai/docs/pleos-only/app-integration-guide/guide/deliver-schema)는 앱 Schema 검토·승인과 action filter를 설명한다. 이 앱의 승인 또는 음성 실행 성공을 뜻하지 않는다. Gleo를 문자·위치·운행 이벤트가 자동으로 들어오는 데이터 버스로 가정하지 않는다. 기존 에뮬레이터의 메뉴/화면 관찰은 이 픽업 흐름 실행 증거가 아니다. 실제 Gleo 연동은 필수 기술 검증 항목이다.

## ‘확실한 우위’의 통과 조건

다음은 **앞으로 확인할 기준의 제안**이며 이번 토너먼트에서 얻은 수치가 아니다. 목표를 낮춰 통과시키거나 토너먼트 우승을 측정 결과로 대신하지 않는다.

- 먼저 기존 픽업 일지로, 기존 채널(카카오톡·만날 장소·Gleo 음성 문자/전화)을 사용했는데도 오대기·추가 확인 연락·미수락 변경 실패가 남은 회차 비율을 측정한다. 문제없이 처리된 변경/지연은 수요로 세지 않는다. 모집 전에 반복성 중단 기준을 고정한다. 예비 기준 제안: 주 3회 이상 픽업하는 쌍에게 2주 동안 이 잔여 불편 회차가 2회 미만이면 주력 사용층으로 보지 않는다. 수요 실측이나 전체 인구 기준이 아니며, 해당 대상층 비중도 보고한다.
- 동일 사용자 쌍이 기존 방식과 제안 흐름을 교차 사용한다. Gleo 음성 문자/전화와 그 차·폰에서 실제 지원되는 공유 기능을 포함한다. 정상 픽업과 실제로 지점변경/준비지연이 발생한 픽업을 구분한다. 반복 이용자 모집과 기간·표본 수는 다음 검증 설계에서 정한다.
- 기준선 대비 픽업 1회당 운전자 확인 연락을 중앙값 30% 이상 줄이는 것을 목표로 한다. 음성 메시지 왕복과 통화도 연락으로 센다. 기준선이 0인 회차는 비율 대신 원시 횟수로 별도 보고한다.
- 오인한 지점에서 기다린 시간과 미수락 변경에 따른 실패가 줄어야 한다. 단순히 대기 자체가 모두 없어져야 한다는 의미는 아니다.
- **양측 합계 능동 조작 시간과 입력 횟수가 증가하지 않아야 한다.** 회차 생성·링크 공유·열기·인증·확인·재시도·실패 후 연락까지 모두 센다. 첫 사용과 재사용을 따로 보고, 짧은 음성 한 번을 터치 한 번과 같은 비용으로 취급하지 않는다.
- 상대의 응답 지연/미참여 때문에 오대기·연락이 늘면 실패다. 익숙한 카카오톡보다 참여가 어렵거나, 상태버튼을 누르는 행위가 불편을 다른 사람에게 옮기면 개발 가설을 재검토한다.
- 실제 Gleo 연동 가능성과 운전자 사용 제한을 확인해야 한다. 모의 음성·버튼 시연으로 통과 처리하지 않는다. 공도에서 실험적으로 조작을 유도하지 않고 안전한 정차 환경에서 기술·입력 부담을 먼저 확인한다.

가장 큰 미해결은 알고리즘이 아니라 **상대가 별도 흐름에 참여할 이유**다. “나왔어”라는 짧은 메시지보다 좋아지지 못하면, 기능을 더 붙이기 전에 이 방향을 중단할 근거가 된다.

## 최종 검수 보완과 추가 경쟁 근거

Claude 최종 검수에서 차내 음성 메시징 기준선 누락을 중요 결함으로 지적했고 Codex가 수용했다. Gleo도 이미 음성 연락 부담을 줄이므로 C02의 우위는 음성 사용 자체가 아니다. 남는 가설은 명시 준비 의사와 미수락/확정 지점 합의를 구별하는 회차 상태다. 짧은 음성 답변으로 충분하다면 우위가 없다.

[카카오맵 2026-05-26 공식 안내](https://kakaomap.tistory.com/449)는 만날 장소·도착 여부·남은거리까지 결합한다. [8월 업데이트](https://kakaomap.tistory.com/457)에서도 기능 유지를 확인했다. [Apple 국내 도입 안내](https://www.apple.com/kr/newsroom/2025/03/apple-brings-additional-find-my-capabilities-to-south-korea/)의 위치공유·안전확인 도착알림과 [Google Maps 공유 안내](https://support.google.com/maps/answer/15437054?co=GENIE.Platform%3DAndroid&hl=en)도 비교했다. Google의 한국 도로 내비 지원을 추정하지 않았고, 네이버·T맵의 동등 기능은 이번 추가 조사에서 확정하지 못했다. 위 자료는 픽업 앱의 위치/도착/만날 지점 자체가 새롭지 않다는 강한 반례다.

상대방 데이터 동의, 최소 보관범위·보존기간, 계정 없는 참여 가능성과 인증, 회차 삭제, 자체 서비스 운영비는 다음 설계에서 확인해야 한다. 무가입이 안전하게 가능하거나 무료 운영이 보장된다고 가정하지 않는다. 이 비용까지 감수할 반복 필요가 없으면 중단한다.


재심에서도 Claude는 **C02 선택 유지에는 동의**했고, 보고서의 차별 범위·반복성 판정에 추가 수정을 요구했다. Codex는 이를 반영했다. 문서에 준비/변경 수락이 없다는 사실은 경쟁 앱의 미지원 증거가 아니다. 개발 착수 전 실제 카카오맵에서 만날 장소 변경 권한, 변경 알림, 상대 확인/수락 절차를 확인해야 한다. 이 기능 확인은 아직 미실행이며, 임의로 시장 공백을 확정하지 않는다.
