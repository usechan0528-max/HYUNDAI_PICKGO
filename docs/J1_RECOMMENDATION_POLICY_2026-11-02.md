# J1 추천 정책 v1

2026-11-02 사용자 요청 “그러면 설계 및 개발 시작해보자”에 따른 로컬 설계·개발. Codex 구현, Claude 독립 검수. 기능 범위는 기존 웹/합성 운행 추천 함수의 정책 정식화다. Android 이식·실제 위치/ETA 연결·학습 모델·새 피드백 화면·외부 전송은 포함하지 않는다.

## 목표와 계약

일반 차주가 콘텐츠를 반복 선택하지 않아도 다음 항목을 준비한다. 기존 `recommend(input)`은 원래부터 `{id, score, reasons}` 추천 레코드 또는 null을 반환하며 이 계약을 유지한다. 카탈로그 원본 객체를 반환하는 함수가 아니다. 모든 기존 호출부에 적용된다. 새 `rankRecommendations(input)`은 policyVersion, 선택 레코드, 전체 순위, 제외 이유, 소진 상태를 반환한다. 원시 위치와 목적지 정보는 결과에 복사하지 않는다. 함수 자체는 재생·저장·네트워크를 실행하지 않는다.

입력: catalog, preferences(topics/byPurpose/likedIds/dislikedIds/dislikedTopics), 호출자가 이미 검증한 context, recent, currentId, 선택적 lastTopic. 입력은 애플리케이션 내부의 JSON 형태 데이터다. SDK 신선도·동의·프로필 검사는 기존 어댑터/세션 책임으로 유지한다. `hypothesis` 문자열만으로 SDK 입력이 인증되는 것은 아니다. 실제 SDK 모드는 계속 unknown을 공급한다.

## 선택 순서

1. ID/주제가 없거나 ID가 중복된 항목은 모두 제외한다. 중복 중 하나를 임의 선택하지 않는다.
2. 기존 testOnly=true 시연 경계를 유지한다. 이것은 운영 콘텐츠 권리 인증이 아니다. playable=false, 명시적 비선호 ID/주제, 현재 재생, recent 항목을 제외한다. 기존 시연 카탈로그의 playable 생략은 재생 후보 허용이며 실제 디코딩 가능 보장이 아니다.
3. 점수 = 주제 취향 + 운행 맥락 적합도 + 명시적 좋아요(1). 취향·맥락 값은 유한 숫자만 인정하고 각각 -5~5로 제한한다. 검증된 최적 가중치가 아니라 고정 실험 정책이다. 좋아요가 반복 입력돼도 가산은 한 번이다.
4. 복수 경로에서는 각 후보 목적별 점수의 최솟값을 유지한다. 확률이 없는 상태에서 평균을 확률처럼 해석하지 않는다. 라벨 없는 후보는 0, 잘못된 후보가 하나라도 있으면 맥락 전체를 사용하지 않는다. 보수적 선택이 다양성을 줄일 가능성은 후속 사용자 평가 대상이다.
5. 동점이면 lastTopic과 다른 주제 우선, 다시 동점이면 ID의 UTF-16 코드 유닛 순서. 무작위 선택이나 입력 배열 순서에 의존하지 않는다. lastTopic은 선택적이며 기존 UI는 아직 공급하지 않는다.
6. 후보가 없으면 exhausted/null. 자동으로 비선호·최근 제외를 풀지 않는다. 기존 cockpit은 명시적 종료, 소진 뒤 새 듣기, 오류 뒤 명시적 재시도에서 recent를 초기화한다. 순위 함수 자체는 recent를 초기화하지 않는다.

반환 레코드 호환성과 선택 정책의 동일성은 다르다. 잘못된/중복 카탈로그 제외, playable=false 제외, 점수 ±5 제한, UTF-16 동점 처리는 의도적으로 강화한 동작이다. 현재 정상 시연 카탈로그·기존 합성 사례의 선택 ID/점수는 변경 전 함수와 별도로 비교한다.

기존 이어듣기는 현재도 추천기를 거치지 않고 저장 계층의 유효한 체크포인트를 우선한다. 새 비선호/재생불가 설정 UI는 아직 없고 rank 함수 입력으로만 지원한다. 이를 향후 UI에 연결할 때는 저장 체크포인트에도 같은 제외 정책을 적용해야 한다. 현재 UI에 비선호 기능이 완성됐다고 표시하지 않는다. `mode=journey`는 후보 경로가 유효한 입력이라는 뜻이며 모든 후보가 라벨 없음일 때도 맥락 점수는 0일 수 있다. 점수 기여는 reasons.contextual로 구분한다. `coldStart`는 해당 항목 점수 근거 없음이며 사용자 전체 이력 유무 판정이 아니다. ranked는 입력 순서와 무관하고 excluded는 진단을 위해 입력 순서를 보존한다.

## 피드백과 연속성

명시적 좋아요/비선호만 입력 계약으로 제공한다. 건너뛰기는 이유가 불명확하고 완청도 선호 확정 근거가 아니므로 자동 학습하지 않는다. 기존 recent는 이번 세션 재생 시작 항목으로서 반복만 억제한다. 피드백 영구 저장을 추가하지 않는다.

QueuePolicy·미디어 수명주기·자동 다음 재생·중단·이어듣기 구현을 변경하지 않는다. 정책 함수는 현재 항목을 교체하지 않는다. 경로 변화 반영과 만료 재검사는 기존 세션/합성 재현 도구의 책임이다.

## 수용 조건 및 검증

- 동일 입력/카탈로그 순서 변경에서 동일 순위; 원본 입력 불변.
- 비선호·현재·recent·잘못된/중복 항목 제외; 소진 때 자동 반복 없음.
- 맥락 불확실/미확인 시 보수적 선택 또는 취향 대안; 실제 SDK 상태/ETA로 순위 변경 없음.
- 숫자 오류가 점수 오염을 만들지 않음; 모든 점수의 구성과 설명 제공.
- 기존 좌표 추정·철회·만료·큐 예산·이어듣기/재생 회귀 통과.
- 합성 시나리오와 사용자 효과 검증을 구분.

실행: `node --test experiments/journey-context/*.test.mjs`, `node experiments/journey-context/recommendation-scenarios.mjs`.

현재 4편 시연 카탈로그와 합성 사례는 정책 동작만 보여 준다. 취향만/시간대/운행 맥락 추천 간 비교 도구는 유지한다. 후속 평가에서는 동일 콘텐츠 집합과 운행 시나리오로 재선택 횟수, 명시적 건너뛰기 이유, 반복 노출, 맥락 오류를 비교해야 한다. 정답을 만든 동일 사례에서 가중치를 맞춘 결과를 사용자 효과로 보고하지 않는다. 실제 사용자 조작 감소·정확도·만족도는 미검증이다.

## 협업과 제약

이전 Opus 5.5 판단은 규칙 정식화 우선·학습형 보류에 동의했고 min 집계의 보수성과 피드백 설계를 지적했다. v1은 집계를 유지하고 제한을 명시하며 명시적 피드백 계약을 추가한다. Dot R004 시각 계약 미확인 결과를 재사용한다. 새 공식 API 질문은 없어 Dot에 중복 과제를 만들지 않는다.
