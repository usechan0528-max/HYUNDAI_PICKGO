# 주차 여석·출차 예측 확장 검토

2026-11-02 KST. 사용자 제안에 대한 Codex 평가와 Claude Opus 5.5 독립 검토. 구현·위치 수집·외부 API 계정 생성은 하지 않았다.

## 판단

도착 준비 카드에 주차장 여석 정보를 연결하는 방향을 조건부 추천한다. 공식/운영사 현황을 기반으로 시작하고 동의한 앱 차량의 관측을 보조 정보로 연구한다. 앱 사용자 입출차만으로 모든 차량의 정확한 여석을 산출하는 방식은 채택하지 않는다. 사용자가 추가 기능을 제안한 것이며 제품 전체 범위를 확정한 것으로 기록하지 않는다.

## 핵심 구분

| 정보 | 의미 | 제한 |
|---|---|---|
| 공식 여석 | 공급자가 특정 시점에 보고한 이용 가능 면수 | 지금이나 도착 시점의 확보를 보장하지 않음 |
| 앱 관측 | 참여 차량 일부에서 관측한 움직임 | 전체 입출차 또는 특정 주차면의 빈자리로 확대 불가 |
| 미래 예측 | 일정 시간 내 출차·가용성의 확률적 추정 | 실측 라벨·표본·정확도·보정 검증 전 사용자 표시 보류 |

논리적으로 다음 여석은 이전 여석+출차-입차에 이용 제한 변화까지 반영해야 한다. 앱 미사용 차량의 입출차와 초기 점유를 모르면 부분 표본만으로 전체 여석은 식별되지 않는다. 예를 들어 3대가 출차해도 5대가 들어오면 빈자리가 늘지 않는다. 이는 설명용 가상 수치다.

주차면에서 이동 시작, 자리 비움, 주차장 출구 통과는 다른 사건이다. GPS와 기어·속도 등의 신호 조합은 후보일 뿐, 특정 신호의 제공·정확성·권한은 아직 확인하지 않았다. 지하 위치 오류·인접 시설 혼동·통신 단절·차량 내 대기·주차면 이동을 출차로 오인할 수 있다. 주차장 단위 집계와 B2층 특정 자리 안내도 서로 다른 문제이며 후자는 위치/면별 인프라 없이 약속하지 않는다.

## 공식 자료 확인

- 서울시는 실시간 주차가능면수 서비스를 이미 제공한다. 여석 숫자 자체의 신규성은 주장하지 않는다. [서울시 안내](https://news.seoul.go.kr/traffic/archives/1869)
- 서울 열린데이터광장의 공영주차 정보 설명은 OpenAPI 제공과 5분 연동 주기, 실제 현황과 차이 가능성을 명시한다. 모든 공급자에 같은 주기를 적용하지 않으며 선택한 API의 최신 계약·필드·이용 조건·갱신 시각은 별도 확인한다. [데이터 안내](https://data.seoul.go.kr/dataList/6/literacyView.do)
- Pleos FusedLocation은 위치 조회·구독·지원 여부 확인 기능을 설명한다. 마지막 위치는 새 측정이 아니고 위치가 없을 수 있다. 문서는 전경/배경 위치 접근 정책을 별도로 보장하지 않는다. 상시 수집 가능성을 전제할 수 없다. [공식 문서](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/FusedLocation/intro)
- 차량 신호에는 API별 조회 권한 확인이 필요하다. 권한 선언만으로 취득·실행 가능하다고 간주하지 않는다. [Vehicle 권한](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle-permission)

## 최소 기능 제안

한 지역 공식 현황 연계 주차장 2~3곳을 대상으로 여석·측정 시각·입구·운영시간·이용 조건을 제시한다. 미수신은 0대가 아니라 확인 불가로 표시한다. 오래된 값은 단순히 흐리게만 하지 않고 현재 가용성 추천에서 제외하거나 갱신 지연으로 명확히 표시한다. 운영/예약/전용 면수와 일반 이용 가능한 면수를 구분한다. 초기부터 차량 표본을 요구하지 않아 초기 사용자 부족 문제를 줄인다.

초기에는 도착 시점 예측을 넣지 않는다. SDK·내비 계약 확인 전 ETA가 자동 제공된다고 가정하지 않는다. 공식 현황 표시와 기존 진입 카드 결합부터 검증한다. 이후 데이터 사용·보관 조건을 확인한 시계열에 단순 기준 모델을 적용하고, 시간 순서로 분리한 검증 자료에서 성능을 평가한다.

후속 폐쇄 파일럿은 한 주차장에서 운영사 입출차 또는 적법한 실측 라벨과 동의 기반 차량 이벤트를 비교한다. 라벨은 예측 대상(자리 비움/출구 통과)에 맞게 정한다. 차량 신호 추가 전후의 성능을 비교해 공공 현황만 쓸 때보다 유용한지 확인한다. 지표는 사건 오탐·누락, 예측 시점별 정확도/확률 보정, 주차장 귀속 오류, 추천 실패율이다. 같은 차량·시간대의 정보 누출과 실시간 값을 미래 정답처럼 사용하는 평가를 막는다.

표본이 적거나 데이터가 오래되면 예측하지 않는다. 정성 구간도 검증 없이 '여유'라고 표시하지 않는다. 공급자 현황에 반영된 출차를 앱 신호로 다시 더하지 않는다. 출차 확률만 보지 않고 도착 전 입차와 추천 쏠림 영향을 함께 검토한다.

## 개인정보와 수집 설계

자발적 참여·동의 철회·삭제·보관기간을 설계한다. 가능하면 차량에서 이벤트를 판정해 주차장 식별자·필요한 시간 범위·신뢰도 등 최소 정보만 전송한다. 서버의 이벤트 역시 개인과 연결될 수 있어 익명 정보라고 단정하지 않는다. 차량별 정확한 위치·출차 예정 시각·동선은 타 사용자에게 공개하지 않는다. 작은 표본은 숨기고 집계·시간 단위의 재식별 위험을 검토한다. 법적 요건 충족 여부는 이번 검토에서 판정하지 않았다.

## Claude 지적과 Codex 처리

- 실측 라벨 부재와 부분 표본의 추가 가치 미입증: 반영. 공식 현황 MVP와 예측 연구를 분리한다.
- 소규모 집계 재식별: 반영. 개별 신호 공개 금지와 부족 표본 숨김을 적용한다.
- Claude의 MVP 시계열 기반 정성 예측 제안: 보류. 정성 예측도 검증 전에는 오도할 수 있어 초기 기능에서 제외한다.
- 차량 크기·충전 필요·ETA를 활용한 차별화 제안: 가설로만 유지. 차량/시설 데이터와 기본 서비스 대비 검증 전 범위를 넓히지 않는다.
- '고통이 분명하다'는 Claude 표현: 사용자 수요가 실측된 것으로 해석하지 않는다.

추천 제품 가설은 '목적지 주변에서 지금 확인 가능한 주차 후보와 올바른 입구를 함께 제공하고, 검증 후 도착 시점의 가능성을 보완하는 도착 도우미'다. 다음 기술 확인은 실제 사용 가능한 주차 API의 관측 시각·가용 면수 정의·지연·이용 조건이며, 실제 위치 수집은 아직 시작하지 않는다.
